# Правила работы с OpenBeekeeper

## Общение и выполнение

- Общаться с пользователем по-русски, кратко и конкретно. Экономить токены.
- Работать самостоятельно, без субагентов, если пользователь явно не попросил иного.
- Запрос на изменение считать поручением выполнить работу. Не останавливаться на плане.
- В пределах поручения самостоятельно исправлять, коммитить и публиковать изменения в репозитории. Не использовать force push.
- Не утверждать, что код проверен на игровом сервере: локальные проверки используют симуляцию.
- Не выдавать окружение разработки за компьютер пользователя или игровой компьютер OpenOS.
- Не менять согласованную политику незаметно. Существенные ограничения описывать прямо.

## Источники договорённостей

- `docs/requirements.md` — требования и ограничения продукта.
- `docs/design.md` — устройство текущей реализации.
- `docs/automation.md` — эксплуатация и команды.
- `docs/architecture.md` — исторический проект; не считать его описанием текущего исполнителя.
- Новые указания пользователя имеют приоритет над этими файлами. При изменении договорённости обновлять соответствующий документ.
- Не переносить старые предположения в требования как подтверждённые факты. Не обещать функции, которых нет в коде.

## Код и поставка

- Целевая среда: Minecraft 1.12.2, OpenComputers/OpenOS, Forestry, Gendustry, AE2; сервер McSkill HiTech может изменять стандартные рецепты и эффекты.
- Поддерживаемые источники: `src/automation.lua`, `src/dashboard.lua`, `src/climate.lua`, `src/climate-data.json`.
- После изменения встроенных исходников выполнять `python3 tools/embed_automation.py`. Не поддерживать отдельно расходящиеся копии встроенного кода.
- Не добавлять обязательных отдельных Lua-модулей на игровой компьютер без необходимости: пакет устанавливает встроенный `openbeekeeper.lua`.
- Документальные изменения не требуют новой версии приложения или пересборки manifest, если файлы поставляемого пакета не меняются.
- Для выпуска сначала коммитить полезную нагрузку, затем строить `package.manifest` через `tools/build_manifest.py` из этого коммита. Revision должен указывать на опубликованный коммит с соответствующими байтами файлов.
- При публикации через API сверять дерево с локальным коммитом и обновлять main с проверкой ожидаемого SHA.

## Проверки

- Запускать минимальные содержательные проверки по изменению. Не писать тесты, повторяющие очевидную реализацию, или тесты для одних формулировок.
- Изменения владения предметами, очереди, восстановления и запретов проверять сценариями переноса, возобновления или конкурирующих задач.
- Команда набора: `python3 -m unittest discover -s tests -q`; для одного сценария добавить `tests` в PYTHONPATH и выбрать конкретный unittest.
- Установленные отдельно зависимости подключать через PYTHONPATH текущего окружения; не зашивать пути рабочего контейнера в проект.
- Перед коммитом проверять `git diff --check`. Для изменений только документации тесты программы не нужны.

## Инварианты

- Не терять и не удалять пчёл при отмене, ошибке или запрете: сохранять владение либо возвращать в МЭ.
- Не повторять автоматически перенос с неопределённым результатом. Пустые входы не доказывают отсутствие внутренней работы.
- Не очищать чужие записи базы и запросы непривязанных интерфейсов.
- Полные снимки МЭ — не чаще одного раза в 20 секунд. Это ограничение не распространяется на настройку точного запроса интерфейса.
- Свободные входы всех механизмов можно предзагружать. Сохранять порядок владения общими выходами и сначала использовать свободные устройства.
- Не зашивать количество пасек или механизмов. Поддерживать несколько механизмов у одного транспозера без отдельного адаптера на каждый.
- Не добавлять обязательный анализ маток и родителей мутатрона ради фильтра эффектов: пользователь выбрал список видов и проверку уже видимых генов.
- Удаление выбранной задачи не должно менять планировщик, запрещать вид или мешать повторному созданию задачи. Сохранённая политика эффектов и условий — отдельная настройка.
