# Привязка модулей

Начиная с 0.6.0 `bees bind` сопоставляет МЭ-интерфейсы и транспозеры по реально
доставленному предмету. Порядок UUID и номера из `bees me` для этого не подходят.
Координаты компонентов через доступный API не раскрываются.

Каждый модуль: один транспозер, один соседний МЭ-интерфейс и одна или несколько
пасек/машин на остальных гранях. Интерфейс должен иметь адаптер в общей сети OC
и подключение к общей МЭ. Одна база данных OC достаточна для всей установки;
дополнительные базы можно оставить. Число модулей не зашито в код.

Поддерживаются промышленные пасеки, обычный/продвинутый мутатрон, импринтер,
пробоотборник Gendustry и анализатор Forestry. Обнаружение продвинутого мутатрона
не означает, что OC умеет выбирать в нём результат мутации.

## Запуск

1. Остановить другие программы управления этими интерфейсами.
2. Убрать запросы и предметы из девяти рабочих слотов интерфейсов рабочих модулей.
   Посторонние интерфейсы с запросами можно оставить: они пропускаются.
3. Положить хотя бы один обычный булыжник `minecraft:cobblestone` в общую МЭ.
4. Выполнить `bees bind`, затем `bees modules`.

Во время проверки не менять инвентари интерфейсов. Пчёл из механизмов убирать
не требуется: программа вообще не читает и не меняет их слоты при привязке.

Программа выбирает свободную ячейку базы, один раз копирует туда описание
булыжника через `store`, затем по очереди выставляет запрос одного предмета
в конфигурационном слоте 9 интерфейсов. Содержимое МЭ через
`getItemsInNetwork` не запрашивается. Для каждого запроса опрашиваются только
локальные инвентари через транспозеры. После обнаружения предмета запрос
снимается; программа ждёт, пока интерфейс вернёт предмет в МЭ. Один булыжник
можно использовать для всех модулей. Таймаут доставки и возврата — по 15 секунд.

Настраиваемых интерфейсов может быть больше, чем рабочих модулей (например,
13 интерфейсов на 9 модулей). Кандидаты — только интерфейсы без запросов во всех
девяти конфигурационных слотах. Их буфер доступен через транспозер только для
рабочих модулей; перед привязкой он должен быть пуст. Посторонний интерфейс без
запросов временно получает запрос маркера: если за 15 секунд маркер не появился
ни в одном рабочем модуле, запрос снимается и поиск продолжается. После привязки
всех модулей остальные кандидаты не проверяются. Порядок UUID не определяет связи.
Посторонний транспозер без пчелиных машин не участвует в привязке, даже если видит
несколько интерфейсов. Если несколько интерфейсов касается именно транспозера с
рабочей машиной, маршрут неоднозначен и привязка безопасно останавливается.

Если кандидатов меньше модулей, буфер рабочего модуля занят, появляется
посторонний предмет либо связь неоднозначна, привязка прекращается. Если все
кандидаты проверены, но связаны не все модули, результат не сохраняется.
Существующая полная таблица и её резервная копия не заменяются частичным результатом.

## Сохранение и восстановление

Таблица: `/home/.openbeekeeper-data/modules`, предыдущая версия — `.bak`.
Строки `interface` хранят адрес транспозера, его грань интерфейса и адрес
МЭ-компонента; строки `machine` — адрес транспозера, грань и тип механизма.
`bees modules` показывает сохранённую таблицу, а не проверку её актуальности.
После перестройки/замены блока нужно заново выполнить `bees bind`.

Перед изменениями записывается журнал `/home/.openbeekeeper-data/bind-pending`.
При ошибке программа пытается снять собственный запрос и очистить только
выделенную ячейку базы. После прерывания выполнить `bees bind-reset`, затем
`bees bind`. Не удалять журнал вручную, пока запрос не снят. Запускать одну
команду управления модулями за раз.

`bees bind` только подготавливает маршруты. Автоматизация запускается отдельно
командой `bees auto`; описание — в [automation.md](automation.md).
